## 🎯 Цель проекта
•	**Какую задачу решает приложение:** Позволяет пользователю играть в классический лабиринт, используя акселерометр устройства для управления движением шарика.

•	**Почему эта задача важна:** Демонстрирует работу с физическими датчиками устройства и создание кастомных графических компонентов (Custom View).

•	**Целевая аудитория:** Любители простых аркадных игр и головоломок.
________________________________________
## 📌 Требования к приложению
**Функциональные требования**
•	Генерация случайного лабиринта при каждом запуске.
•	Управление шариком путем наклона устройства.
•	Обнаружение столкновений со стенами.
•	Условие победы при достижении финиша (зеленая зона).
**Нефункциональные требования**
•	**Производительность:** Плавная отрисовка 60 FPS.
•	**Удобство использования:** Интуитивно понятное управление.
•	**Надёжность:** Корректная работа при изменении ориентации и жизненного цикла Activity.
________________________________________
## 🧠 Общая архитектура
•	**Выбранный подход:**
–	Архитектура на основе взаимодействия Activity и Custom View (упрощенная модель MVC).

•	**Почему выбран именно он:** Для небольшого игрового проекта это обеспечивает минимальную задержку между получением данных от датчика и обновлением экрана.

•	**Основные компоненты системы:**
–	`MainActivity`: Управление датчиками и жизненным циклом.
–	`MazeView`: Логика лабиринта, отрисовка и физика шарика.

## 🧩 Подробное описание классов
### 📌 Класс: MainActivity
**Роль:**
Главный контроллер приложения.
**Ответственность:**
Инициализация SensorManager, подписка на данные акселерометра, обработка системных событий.
**Основные методы:**
- `onCreate()` — настройка UI и инициализация датчиков.
- `onSensorChanged()` — получение данных о наклоне и передача их в MazeView.
- `onGameWon()` — вывод диалогового окна победы.
**Взаимодействие с другими классами:**
Передает координаты наклона в `MazeView` и слушает событие завершения игры.
________________________________________
### 📌 Класс: MazeView
**Роль:**
Графическое ядро и игровой движок.
**Почему используется:**
Необходимо реализовать кастомную отрисовку лабиринта и шарика, недоступную через стандартные виджеты.
**Ответственность:**
- Генерация лабиринта (алгоритм Recursive Backtracking).
- Обработка столкновений.
- Отрисовка элементов на Canvas.
________________________________________
## 🔄 Диаграмма работы приложения
1. Запуск приложения -> `MainActivity` запрашивает данные акселерометра.
2. `MazeView` генерирует лабиринт и рисует шарик в начальной точке.
3. Пользователь наклоняет устройство -> `MainActivity` ловит событие.
4. `MazeView` обновляет позицию шарика и проверяет стены.
5. Шарик касается зеленой зоны -> `MainActivity` показывает "You Won!".

## 🎨 UI/UX анализ
•	**Почему интерфейс сделан именно так:** Максимальный фокус на игровом поле. Черные стены на белом фоне обеспечивают высокую контрастность.

•	**Какие принципы использованы:**
–	**Простота:** Нет лишних меню и кнопок.
–	**Логичность:** Шарик катится в ту сторону, куда наклонён экран.
–	**Доступность:** Яркие цветовые индикаторы (Красный — игрок, Зеленый — выход).
________________________________________
## ⚙️ Работа с потоками
•	**Используются ли:**
–	Main Thread (UI Thread)
•	**Почему выбран этот способ:** Для данной сложности проекта стандартного UI-потока достаточно для обработки событий сенсора и перерисовки Canvas.
•	**Как предотвращаются:**
–	**зависания (ANR):** Код обработки сенсора оптимизирован и не содержит блокирующих вызовов.
–	**утечки памяти:** Слушатель сенсора отключается в `onPause()`.
________________________________________
## 💾 Работа с данными
•	**Где хранятся данные:** В оперативной памяти (массив `maze[][]`).
•	**Почему выбран этот способ:** Лабиринт генерируется заново для каждой сессии, хранение на диске не требуется.
